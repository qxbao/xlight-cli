## Wave 2: what was verified directly from source

Read `openai/codex` (Apache-2.0) @ `1cc7e2361237ce7244430ee1d581c77f95c57ac8`,
`codex-rs/core/src/client.rs`:

- **H** Request path: `/responses` (relative, appended to `api_provider`'s base) —
  `tracing::Span::current().record("api.path", "/responses")` in `stream_responses_api`.
- **H** Request body (`build_responses_request`, lines ~885-1007): `model`, `instructions`, `input`,
  `tools`, `tool_choice: "auto"`, `parallel_tool_calls`, `reasoning: {effort, summary}`,
  `store: false`, `stream: true`, `stream_options` (optional), `include:
  ["reasoning.encrypted_content"]`, `service_tier`, `prompt_cache_key`, `text` (verbosity/output
  schema), `client_metadata`, `access_programs`. `crates/provider-codex/src/wire/request.rs`
  implements exactly this part (omitting `client_metadata`/`access_programs`/`prompt_cache_key`/
  `service_tier` — internal to Codex CLI, not needed for Phase 0).
- **H** Header constants exist: `OpenAI-Beta`, `x-codex-installation-id`, `x-codex-routing-hint`,
  `x-codex-turn-state`, `x-codex-turn-metadata`, `x-codex-parent-thread-id`, `x-codex-window-id`,
  plus an "originator" header attached via `codex_login::default_client::add_originator_header`
  (exact header name **U** — could not read `codex-rs/login` in this pass).
- **H** 401 → `handle_unauthorized` runs auth recovery then retries (`stream_responses_api` loop).
- **U** (could not read in this pass, the codebase has been refactored substantially since the older version): the exact
  base URL of the ChatGPT backend (`api_provider`/`ApiProvider` resolution logic lives elsewhere,
  not found in `client.rs`), and the exact quota endpoint. Keeping the **M** value from the earlier
  spike (`https://chatgpt.com/backend-api`, path `/wham/usage`) — `CodexEndpoints` in
  `lib.rs` allows overriding without code changes once live-check results are available.
- Codex also has a WebSocket transport for Responses (`stream_responses_websocket`) — **not**
  implemented in Phase 0 (only POST + SSE over HTTP, as with OpenCodex/the public `openai-api`).

Read OpenCodex (MIT) @ `3cc34e1181926b64331490fdcfee162ffb62fe73`:

- **H** ChatGPT OAuth (`src/oauth/chatgpt.ts`): client id `app_EMoamEEZ73f0CkXaXp7hrann`,
  authorize `https://auth.openai.com/oauth/authorize`, token
  `https://auth.openai.com/oauth/token`, scope
  `openid profile email offline_access api.connectors.read api.connectors.invoke`, callback
  `http://localhost:1455/auth/callback`, extra param `codex_cli_simplified_flow=true`,
  `id_token_add_organizations=true`.
- **H** Device-code grant (`src/oauth/chatgpt-device.ts`) — **not RFC 8628**: step 1
  `POST https://auth.openai.com/api/accounts/deviceauth/usercode {client_id}` →
  `{device_auth_id, user_code, interval}`; step 2 poll
  `POST https://auth.openai.com/api/accounts/deviceauth/token {device_auth_id, user_code}` → 403/404
  = pending, 200 = `{authorization_code, code_verifier}` (verifier **generated by the server**, not the
  client); step 3 exchange using a regular `authorization_code` grant (same token endpoint,
  `redirect_uri = https://auth.openai.com/deviceauth/callback`). Verification URL shown to the user:
  `https://auth.openai.com/codex/device`.
- **H** Extracts `chatgpt_account_id` from the JWT (`extractAccountId`): prefers the top-level claim
  `chatgpt_account_id`, then the namespace `https://api.openai.com/auth.chatgpt_account_id`, finally
  `organizations[0].id`; tries `id_token` first, `access_token` second. Decoding **does not verify the
  signature** — it's used only as a client-side routing hint, not a trust boundary (authenticity is confirmed
  via the upstream's 200/401 response).

## Notes (retained from the initial spike)

- Codex CLI credentials: `~/.codex/auth.json` (`auth_mode`, `OPENAI_API_KEY`,
  `tokens{id_token,access_token,refresh_token,account_id}`, `last_refresh`) or keyring service
  "Codex Auth" depending on `cli_auth_credentials_store = file|keyring|auto|ephemeral` (H). `$CODEX_HOME`
  changes the directory. `crates/provider-codex/src/auth.rs` only reads the file (does not read the keyring — Phase 0).
- The refresh token rotates ⇒ import & own (D-017) may force the Codex CLI to log in again — warn
  the user.
- Rate limit / quota (source: `codex-rs`, but back to **U** after the Wave 2 read — these header
  strings were not found in the current `client.rs`; kept as in the earlier spike since they may live in
  another module not yet read):
  - Headers `x-codex-primary-{used-percent,window-minutes,reset-at}`, `x-codex-secondary-*`,
    `x-codex-credits-{has-credits,unlimited,balance}`, `x-codex-rate-limit-reached-type`.
  - SSE event `codex.rate_limits` (has `plan_type`).
  - `GET {base}/wham/usage` (ChatGPT base) or `/api/codex/usage`.
- Port source: OpenCodex `src/oauth/{pkce,callback-server,chatgpt,chatgpt-device}.ts`,
  `src/codex/refresh.ts`, `src/adapters/openai-responses*` (PLAN §4.5). **Not** porting
  `src/codex/account-*` (pooling).
- Official reference: `openai/codex` (Apache-2.0 — compatible with GPLv3, D-028). Porting is allowed provided the
  Apache-2.0 notice is kept + changes are recorded, noted in `THIRD_PARTY.md`.

## Live verification checklist (do this manually with a real account — do NOT run in CI/agent)

Before removing the U/M labels above, run the real `codex` CLI (network sniff via mitmproxy or
`RUST_LOG=trace`) or use `xlightcli dev probe codex "hello"` once the Wave 2 auth crate is done, and
confirm:

1. The real base URL of the ChatGPT backend for `/responses` (is it really
   `https://chatgpt.com/backend-api`, or is there a different `/codex` prefix?).
2. The exact `/usage` endpoint (`/wham/usage` vs `/api/codex/usage` vs something else) + the real body shape
   (the field table in `crates/provider-codex/src/quota.rs` is currently only a best-effort parser).
3. The real rate-limit header names (is `x-codex-primary-*` correctly named, is there an
   `x-codex-secondary-*`) and whether they appear on the `/responses` HTTP response or only on `/usage`.
4. The real shape of the SSE event `codex.rate_limits` (field `plan_type`, `rate_limits.primary.*`, does it
   match the fixture `tests/fixtures/rate_limit.sse`).
5. The real "originator" header name (`crate::consts::HEADER_ORIGINATOR = "originator"` is currently just a guess) —
   needs reading `codex-rs/login` (couldn't be read in this pass).
6. Try a real browser OAuth run (once `xlightcli_auth::oauth::LoopbackServer` +
   `exchange_code_for_token` are implemented by Wave 2) and a real device-code run to confirm
   the `authorize_url`/device grant still matches OpenCodex's description (the API may have changed since OpenCodex
   was ported).
7. Confirm whether `auth.json`'s `tokens.access_token` is really always a 3-part JWT (so that
   `decode_jwt_payload` doesn't silently fail) and whether the `account_id` field is always present or must fall back to the
   JWT.
